### Q1: Canonical graph

Use a successor traceability configuration (V5), with explicit project-relative
requirement/UAT/source/test discovery scopes and generated-source mappings.
Historical V1–V4 readers preserve their original semantics. Adoption explicitly
selects V5; no failed V5 parse falls back to a historical parser.

Keep requirement declarations in their existing Markdown owners. Declare stable
obligation IDs beside their conditions and requirement references. Declare stable
acceptance IDs beside their UAT procedures and obligation references. Test and
code annotations identify their own stable unit and the acceptance or obligation
respectively. Extend the existing `Traceability: <role> <target> from <kind> <id>`
syntax, with explicit kinds and role validation; do not infer IDs from paths.
Discovery inventories all declared acceptances in configured UAT scopes, including
ones without an incoming test edge. Multiple edges may share one source unit.

Structural checks prove identities, attachment, references and missing edges.
They never prove behavioral adequacy. Review attestations bind their assessed
IDs and graph/input identity to the reviewed candidate. Unknown adequacy remains
unresolved. Validation identifies its claimed test/acceptance scope and actual commands;
review checks that those commands execute the claimed tests. An unrelated
passing command cannot discharge a gap. No new cross-runner reporting protocol
is required: use runner results and configured no-test/skip failure options. Tests may be unit or
integration. No minimum per-layer quota survives V5 adoption.

### Q2: Validation and review

Implement a typed Git-tag component that runs explicit command/argument arrays
from the repository root, captures exit and termination outcomes, and tags only
the exact clean commit tested. Recheck HEAD and source cleanliness after execution;
refuse passing certification if tracked inputs changed. Commands may write ignored
runtime output. A command with unknown test selection or unaccounted skips cannot
establish the associated acceptance coverage merely by returning exit zero.

Use versioned JSON in annotated tags, with a unique name below
`ponytail/validation/<campaign>/`, a generated run identifier, exact commit,
focused/final purpose, covered IDs, command arrays, timestamps, result and review
references. Detailed output stays in ignored temporary storage; tag payloads stay
compact. Never overwrite tags. Corrections use new tags; explicit revocation
references invalidate earlier certificates. No signatures or remote publication
are implicitly required. Cross-check the tag target against its payload.

Review attestations identify the independent reviewer, exact reviewed candidate,
assessed IDs and verdict. They attest semantic adequacy, not command execution.
A passing tag is an attestation, not a tamper-proof guarantee: the adversarial
review and independent final run remain necessary.

### Q3/Q5: Minimal coordination

Native Codex tools own session identity, state, messages and worktrees. The
coordinator keeps one compact assignment roster in its host context/recovery
record: campaign, monotonically increasing sequence, thread ID, assigned IDs,
branch and blocker/ready/completion status. Do not mirror host activity in a new
Ponytail membership table. Reconcile the roster against native sessions before
replacement or reassignment; unknown activity is not proof of termination.

A worker is DONE only after its delivery is accepted into the integrated branch.
Idle unfinished workers are resumed; genuinely blocked workers retain their
assignment and replacement workers receive other compatible work. Three-letter
assignment names and DONE prefix follow the design record. Check native state
on completion/blocker messages and on bounded waits; use a one-minute service
sweep where the host supports it. A supported heartbeat is a recovery trigger,
not a guarantee of exact scheduling or uninterrupted execution.

Keep project-scoped graph assessment and timestamped observations in the existing
local operational database, never tracked JSON. Store only what is needed for
scope identity, assessments, monitoring and final acceptance. QA failure reopens
repair work; the coordinator independently reruns the complete configured suite
after the last repair. Final acceptance requires all workers DONE, exact zero,
adequate review and a new passing full-QA certificate on the integrated candidate.

### Q4: Instability

Compare lexicographic vectors on the same scope over 30 minutes of active time.
Report net regression if the latest value exceeds the oldest observation in that
window. Report stagnation if no new minimum occurs during that interval. Record
scope amendments and acknowledged external-wait intervals explicitly; exclude
wait time and restart the comparison baseline for changed scope. Report reopening
of previously closed gaps as explanatory churn, without inventing a numerical
churn threshold. Alerts request diagnosis; they neither cancel work nor hide gaps.
Retain a bounded operational observation window and latest accepted state.

### Q6: Retirement and adoption

Retire the entire swarm CLI chapter and the old campaign dispatch, lease, review
queue and publication machinery from executable exports. Preserve necessary
historical readers with their physical meanings and explicit read-only entry
points. Do not reset existing database rows, delete branches/worktrees, or rewrite
historical certificates. Active projects adopt explicitly after unfinished work
has been inventoried and retained; installation alone does not migrate clients.

The authorized Gwen coordinator performs Gwen's adoption after installation,
including assessment of pre-existing workers and branches. This session changes
Ponytail; it does not silently edit Gwen or seize unrelated historical sessions.

## Typed implementation boundaries

The structural graph component owns discovered typed entities, relationships and
findings. It performs no Git, database, test execution or host-session actions.
The source discovery adapter owns parse errors, source locations and generated
mappings; the existing index adapter projects that same graph into query rows.
Do not duplicate graph validation in the index or create a competing manifest of
edges. TSTS owns attachment to actual TypeScript declarations.

The validation component owns process execution and annotated-tag read/write.
Its requests have a version, campaign identity, focused/final purpose, exact
candidate, covered IDs, explicit command arrays and review references. Results
record process exit/signal, timing and the declared validation scope. Store
runner counts when available; never invent missing counts or interpret exit zero
as evidence for a test that the command did not run. Commands are
executed without an implicit shell; a deliberately configured shell command is
explicit in the argument array. The tag target and request candidate must agree.
A failed final run is not an acceptance certificate. Host review attestation
references and worker completion observations are inputs to acceptance, not
invented by this component.

The campaign component owns assessment and monitoring over an explicit set of
requirement IDs and an exact integrated revision. It consumes the canonical
graph, candidate-bound review and validation results; it never creates sessions.
Native observations supplied by the coordinator establish that all campaign
workers are DONE before final acceptance. A timestamp alone does not establish
that a worker stopped. Assessments cannot turn malformed graph or unknown
coverage into zeros. Scope changes invalidate the previous scope comparison.

Keep the normal `campaign init/status/reconcile/accept/close` entry points only
where they implement these adopted operations. `integrate` must validate the
current base, candidate/review/tag identity and graph before a serialized
fast-forward, and return the resulting revision and completeness vector. It
must not rebase, review, execute worker repairs or publish remotely. Final
`accept/close` must validate a freshly coordinator-run full certificate and
worker completion; intermediate acceptance must not set campaign DONE. The
same typed implementation serves CLI and MCP; host tools remain outside it.

Use a versioned, project-local campaign configuration for target parallelism and
named full QA command arrays. Reuse existing command ownership where present;
missing full QA configuration is unresolved, not an empty passing suite. Store
current scope/assessment and a bounded 30-active-minute observation window in
the existing local PostgreSQL database. No new service, global inventory scan,
session membership table or append-only JSON source ledger is needed.

The declaration/call-site inventory confirms `cli/ponytail` dispatches campaign
and swarm through `src/rolling-operations.js` and `src/swarm-info.js`;
`ponytail-mcp/rolling.ts` imports the same registry/operations; `src/cli-help.ts`
feeds the generated command registry; `scripts/build-runtime.ts` owns compiled
launch paths. S05 must reconcile these owners together. `registry.tsv` owns the
three retired/replaced exported skills and installation derives from it.
