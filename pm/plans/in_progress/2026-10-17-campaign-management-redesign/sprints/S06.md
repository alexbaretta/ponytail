## Acceptance and validation

Run configured build-impact selections and required affected integration Arcs.
Final core acceptance is `npm test`, rule-copy and version checks, with registry,
manifests/adapters, generated runtime, structural/indexed traceability, TSTS,
installers, MCP and bundled-subproject checks accounted for once. Fix any required
focused-selection configuration gap instead of substituting a broader command.

Required evidence: graph coverage cannot mask missing acceptances; no fake T/I
decrease; exact review/tag/candidate identity; honest disturbances/monitoring;
blocked worker retention/replacement; no stale or duplicate integration; read-only
historical compatibility; and no tracked validation output or evidence-only
commits produced by the adopted workflow. Do not publish a release or tags to a
remote, rewrite history, or install globally as an implicit acceptance step.

Final acceptance remains pending if actual host continuity cannot be demonstrated
under the approved pilot. The coordinator itself independently executes and
verifies final automated QA; worker tags cannot replace it. A blocked or
unfinished individual worker prevents campaign DONE. Full QA failures return the
coordinator to servicing repair assignments and require another full run on the
repaired candidate. All sprint outcomes are currently planned, not implemented.
