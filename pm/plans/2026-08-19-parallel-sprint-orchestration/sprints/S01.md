## Objective

Define the portable policy for atomic design, parallel sprint planning,
implementation-agent handoff, deterministic dispatch, ownership, and
reconciliation.

## Delegation

- Intended owner: one policy-capable subagent after plan approval.
- Implementation-model handoff: retain this sprint with a policy-capable model
  because its tasklets make the architectural decisions that later enable
  cheaper implementation agents.
- Interference boundary: this sprint alone owns the canonical skill document,
  its focused policy-contract test, and its tasklet scheduling metadata.

## Questions

- No open questions. The plan records the approved design inputs and the
  execution approval remains pending at plan level.

## Feature F01: Atomic planning contract

Acceptance: The skill makes tasklet atomicity and implementation readiness
mechanically reviewable before delegation.

### [DONE] Tasklet S01-F01-T01: Define Atomic Tasklet Eligibility

- Edit `skills/plan-execution/SKILL.md` only.
- Define one tasklet as exactly one type definition, class envelope, method or
  function, controller-to-service endpoint, focused fixture, or validation
  gate.
- Preserve the absence of a hard line limit.
- Require a split-or-justify review when the orchestrator predicts more than
  1,000 new lines.
- Reject tasklets that combine independently implementable declarations.
- Validation: the focused policy-contract test added in S01-F03 must identify
  the atomic units and scrutiny threshold.

### [DONE] Tasklet S01-F01-T02: Define Implementation-Ready Design Records

- Edit `skills/plan-execution/SKILL.md` only after S01-F01-T01.
- Require each tasklet to name exact declarations, structures, types,
  algorithm, control flow, invariants, errors, existing calls, tests,
  configuration synchronization, and exclusions before implementation.
- Permit the orchestrator or a planning subagent to author the record, with
  orchestrator review before implementation handoff.
- Prohibit an implementation agent from silently choosing missing structural
  or algorithmic behavior.
- Permit direct implementation when preparing the handoff is predicted to be
  more expensive, provided the sprint records the reason and retains a capable
  agent.

## Feature F02: Parallel sprint orchestration

Acceptance: The skill defines a single portable ownership and dispatch
lifecycle that keeps parallel changes disjoint and final state authoritative.

### [DONE] Tasklet S01-F02-T01: Define Two-Phase Sprint Metadata Contract

- Edit `skills/plan-execution/SKILL.md` only after S01-F01-T02.
- Make the marked JSON block in each sprint the canonical identity, planning
  lifecycle, execution lifecycle, dependency, scope-root, and exact-path
  contract.
- Define the planning states, execution states, and conditional absence of
  execution metadata before detailed planning is ready for review.
- Keep planning dependencies separate from execution dependencies.
- Define exact repository-relative scope-root and path syntax.
- Require all production, test, generated, configuration, and sprint-record
  paths to be declared.
- Require the orchestrator to reassign and revalidate an undeclared path
  before that sprint edits it.

### [DONE] Tasklet S01-F02-T02: Define Parallel Planning Lifecycle

- Edit `skills/plan-execution/SKILL.md` only after S01-F02-T01.
- Define the orchestrator-owned sprint stub: intent, acceptance criteria,
  scope, exclusions, candidate roots, global contracts, planning dependencies,
  questions, and planning deliverables.
- Require the planning-readiness selector and parallel assignment of ready
  stubs to separate instances of the strongest available planning model.
- Limit a planning agent to read-only repository inspection plus edits to its
  assigned sprint and tasklet metadata.
- Require local architecture, exact paths, atomic tasklets, focused validation,
  implementation capability guidance, and discovered cross-sprint relations.
- Reserve unspecified shared or public contract decisions and planning
  approval to the orchestrator.

### [DONE] Tasklet S01-F02-T03: Define Implementation Dispatch And Model Selection

- Edit `skills/plan-execution/SKILL.md` only after S01-F02-T02.
- Replace the assumption of linear sprint order with a dependency graph.
- Require the orchestrator to run the skill-local readiness tool, dispatch
  ready sprints up to safe runtime capacity, and repeat after reconciliation.
- Prefer one subagent per ready sprint and the least expensive available model
  reasonably expected to implement the prepared tasklets.
- Permit a documented non-delegation decision only for predicted coordination
  cost, insufficient model capability, resource contention, or quality loss.

### [DONE] Tasklet S01-F02-T04: Define Ownership And Reconciliation

- Edit `skills/plan-execution/SKILL.md` only after S01-F02-T03.
- Require orchestrator reconciliation of each planning wave before approval or
  implementation dispatch.
- Reserve the plan manifest, Git index, selective commits, cross-sprint
  reconciliation, and final acceptance to the orchestrator.
- Limit a sprint agent to its declared implementation paths and sprint file.
- Require tasklet-sequential execution within each sprint, focused evidence,
  `READY_FOR_REVIEW` handoff, and journal closure when configured.
- Require orchestrator inspection and selective commit before `DONE`.
- Preserve the existing approval, scope-growth, testing, and stop conditions.

### [DONE] Tasklet S01-F02-T05: Define Completed Tasklet Graph Result

## Feature F04: Persistent journal authorization

Acceptance: The canonical journaling policy requests the exact authority
needed to persist sandbox access without implying that plan approval or local
rules can exceed the user's or administrator's authority.
