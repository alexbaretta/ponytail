# S01: Checkpoint Sprint Orchestration

- Status: `DONE`
- Dependencies: none.

## Objective

Replace parallel sprint implementation with one sequential sprint checkpoint
and select deterministic exact-path-disjoint tasklet waves inside that active
sprint. Preserve physical V1 readers and make V2 the only metadata written
after this sprint.

## Local Architecture

- `ready-sprints.js` remains the sole sprint metadata reader and readiness
  selector. V1 remains an exact physical reader with its legacy dependency
  scheduling and `planned_paths`. V2 retains the V1 top-level and planning
  shapes, but non-null execution contains exactly `status`, `depends_on`, and
  Boolean `tasklets_reviewed`. A plan must use one physical sprint version
  throughout; mixed versions are rejected.
- Planning readiness may still expose multiple dependency-ready draft sprints.
  Execution readiness validates numeric sprint-file order and returns at most
  the earliest unfinished sprint, only after every predecessor is `DONE` and
  the active sprint's tasklets are reviewed.
- `next-tasklet.js` is renamed to the canonical `ready-tasklets.js` selector.
  V1 retains exact scalar selection. V2 adds top-level feature records and
  makes tasklet `planned_paths` the sole exact write-path owner, then emits a
  deterministic maximal disjoint wave.
- Each V2 feature names `depends_on` features and exactly one
  `validation_tasklet`. That tasklet directly depends on every other tasklet
  in its feature and may own focused-test paths; a pure validation gate may
  have no write paths. Every other tasklet has at least one exact
  repository-relative path. A tasklet is ready only after its hard
  dependencies and dependency-feature validation tasklets are `[DONE]`.
- V2 graph validation rejects planned-path overlap within or across features
  unless one tasklet transitively depends on the other through the effective
  tasklet and feature-gate graph. Ordered overlap remains valid.
- V2 ranks ready tasklets with the existing risk, prior-affinity,
  unfinished-descendant, remaining-depth, and ID criteria, then greedily keeps
  candidates whose planned paths do not intersect the current wave. It emits
  `{"next":[...],"criteria":{...}}`; completion remains `{"next":null}`.
- Implementers edit only their frozen implementation paths and return evidence.
  The orchestrator alone changes shared plan/sprint/tasklet records, stages,
  reconciles, validates feature and sprint convergence, and commits.
- This S01 stays physical V1 because V2 cannot schedule its own reader
  implementation. It is not migrated later. Ordinary records created after
  S01 use V2.

## Pre-Implementation Atomicity Review

- `[RESOLVED]` Each tasklet owns one policy section, selector module envelope,
  focused test fixture, manifest edit, generated synchronization operation, or
  validation gate. Its exact files, inputs, behavior, proof, and exclusions are
  stated below.
- `[RESOLVED]` F01, F02, and F03 write disjoint paths and may start in parallel.
  Tests follow their owning implementation. F04 waits for all canonical inputs;
  its manifest, policy-test, and generated-copy paths are mutually disjoint.
- `[RESOLVED]` Producer-consumer dependencies are explicit even across disjoint
  paths. No tasklet relies on line-range ownership, import inference, globs, or
  aliases.
- `[RESOLVED]` Any repeated planned path is transitively ordered in the
  effective dependency graph; unordered overlap is rejected before dispatch.
- `[RESOLVED]` F02-T02 and F03-T02 are their features' focused convergence
  gates. F04-T02 pins the policy contract, and F05-T01 is the sole sprint
  convergence gate on the reconciled tree.
