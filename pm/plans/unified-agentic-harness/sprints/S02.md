# Sprint S02: Establish The Isolated Core

Status: `PENDING`

## Objective

Separate live-development behavior from optional benchmark machinery and
establish one canonical source for Ponytail's portable policy and local
project configuration.

## Dependencies

- Sprint S01 is `DONE`.
- Decisions D05 through D18, D20, D24 through D26.

## Questions

No open questions.

## Feature F01: Isolate Benchmarks

Acceptance criteria:

- Core installation, tests, packaging, and publication do not execute or
  provision benchmark code.
- Benchmark assets remain under `benchmarks/` with their own documented
  commands and dependencies.
- Core documentation does not use benchmark results as an acceptance
  dependency.

### [ ] Tasklet S02-F01-T01: Separate Package Commands

Change the root package command contract so ordinary tests execute only
core tests. Give benchmark validation its own explicit command and keep
benchmark-only dependencies outside the core dependency graph. Add
focused package-script assertions.

### [ ] Tasklet S02-F01-T02: Separate Continuous Integration

Remove benchmark dependency provisioning from the core CI job. Add an
independent optional benchmark-validation job or workflow whose failure
does not change the core dependency contract.

### [ ] Tasklet S02-F01-T03: Move Benchmark Tests

Move benchmark-grader tests out of the core `tests/` directory and into
`benchmarks/`. Preserve their assertions under the benchmark command and
prove the core test glob no longer selects them.

### [ ] Tasklet S02-F01-T04: Separate Benchmark Documentation

Remove benchmark claims and operational details from core installation
and development instructions. Keep benchmark claims, assets, dependency
setup, and reproduction instructions owned by `benchmarks/`.

## Feature F02: Establish Canonical Policy

Acceptance criteria:

- One repository-neutral source owns portable always-on policy.
- Compaction levels affect only aggressive compaction.
- Ponytail's root `AGENTS.md` contains project-local configuration and
  skill bindings rather than a duplicate portable ruleset.
- Generated and runtime consumers preserve the canonical semantics.

### [ ] Tasklet S02-F02-T01: Rewrite Canonical Ponytail Policy

Rewrite `skills/ponytail/SKILL.md` as the canonical portable policy.
Apply decisions D05 through D17, keep all non-compaction rules always on,
and limit `lite`, `full`, and `ultra` to compaction intensity.

### [ ] Tasklet S02-F02-T02: Configure The Ponytail Repository

Rewrite root `AGENTS.md` as Ponytail's project-local configuration. Name
the management root, structure owner, commands, validation boundaries,
temporary path, absent cloud responsibilities, and local skill bindings.

### [ ] Tasklet S02-F02-T03: Document Repository Structure

Add the project-local repository structure and ownership document named
by `AGENTS.md`. Record core, benchmark, adapter, generated, management,
temporary, and publication ownership without duplicating commands.

### [ ] Tasklet S02-F02-T04: Consume Canonical Policy At Runtime

Change the shared instruction builder to load the canonical Ponytail
policy rather than a portable copy in root `AGENTS.md`. Preserve mode
selection while keeping non-compaction policy invariant across modes.

### [ ] Tasklet S02-F02-T05: Prove Policy Conformance

Add focused tests proving all modes retain the always-on rules, only
compaction changes by level, and root project instructions are not used
as the portable runtime payload.
