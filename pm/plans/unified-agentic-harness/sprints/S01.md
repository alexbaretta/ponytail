## Question Queue

Questions are asked one at a time. Record the user's answer under the
owning question and change its marker to `[RESOLVED]` before asking the

### [RESOLVED] Q01: Testing Minimum

Ponytail prescribes one minimal runnable check, discourages fixtures and
test frameworks, and exempts trivial one-liners. The harness assigns
focused, feature, sprint, and final proof according to affected behavior
and host configuration.

Decision:

- Retain the existing `plan-tasklets` unit and integration testing
  cadence.
- Remove Ponytail's one-check limit, prohibition on fixtures or test
  frameworks, and trivial-change test exemption.
- Assign proof to the smallest level that can meaningfully own it.
- Allow broader checks to be deferred only to a named owning gate.

Source: user approval in the Q01 discussion.

### [RESOLVED] Q02: Requirement Substitution

Ponytail says to ship a reduced implementation and question a complex
request afterward. The harness stops before substituting a materially
different result or crossing an approval boundary.

Decision:

- The agent SHOULD choose the simplest implementation that fully
  satisfies the approved requirements and constraints.
- Compare conforming implementations by minimizing conditional branches
  first, then minimizing lines of code among implementations with the
  same branch count.
- Simplicity never permits reduced behavior or a materially different
  result.
- Obtain user approval before omitting or changing a requirement to
  reduce complexity.

Source: user decision in the Q02 discussion.

### [RESOLVED] Q03: Files, Abstractions, And Sources Of Truth

Ponytail prefers the fewest files and no unrequested abstractions. The
harness requires declared ownership, shared sources of truth, contract
types, and adapters when the actual architecture needs them.

Decision:

- Use as few files as necessary given architectural requirements and
  best practices.
- Make a conscious effort to avoid file proliferation and sprawl.
- Avoid files whose only purpose is to re-export names defined
  elsewhere.
- Permit a re-export-only file only when that specific file serves a
  key architectural purpose.
- Preserve required ownership, contract, source-of-truth, and
  host-project boundaries.
- Prohibit aliases that give an existing declaration, type, value,
  module, or import another name. This includes TypeScript
  `import { x as y }` renaming.

Source: user decision in the Q03 discussion.

### [RESOLVED] Q04: Deletion Authority

Ponytail prefers deletion over addition. The harness requires explicit
authority for destructive actions and file deletion.

Decision:

- A clean tracked file whose contents are committed may be deleted
  within approved scope without separate deletion authorization.
- Explicit user authorization is required before deleting an untracked
  file or a tracked file containing uncommitted edits.
- Deletion remains subject to correctness, architecture, provenance,
  and scope requirements.

Source: user decision in the Q04 discussion.

### [RESOLVED] Q05: Output And Communication

Ponytail prescribes code first and at most three short explanatory
lines. The harness requires evidence, progress communication, plan
maintenance, and full requested explanations.

Decision:

- Retain the objective of minimal explanation without imposing a fixed
  line limit.
- State the outcome and verification result.
- Report decisions made without prior agreement, debatable choices,
  meaningful alternatives or tradeoffs, deviations, unresolved risks,
  and points where user guidance would improve the result.
- Do not narrate routine implementation, repeat established information,
  or add generic summaries.
- Do not announce intended actions, research, inspection, tool use, or
  reasoning process.
- Begin work silently. Send an intermediate update only for a material
  finding, risk, blocker, required user action, or decision-relevant
  partial result.
- Answer explicit requests for explanation fully.
- Apply the overarching rule, "Do not repeat yourself," to both code and
  communication.
- Maintain one canonical implementation and do not duplicate the same
  code in multiple places.

Source: user decisions in the Q05 discussion.

### [RESOLVED] Q06: Deferred-Debt Recording

Ponytail introduces `ponytail:` code comments and a debt-harvesting
skill. The harness supports host-configured project-management and bug
artifacts.

Decision:

- Add a root `tech_debt.md` document to the combined Ponytail
  repository.
- Use it as Ponytail's canonical local technical-debt record.
- Prefer recording technical debt directly in `tech_debt.md`.
- Permit exceptional inline markers using `tech-debt:` in the
  language's ordinary comment syntax.
- Do not use the branded `ponytail:` marker.
- An inline marker does not replace the canonical document entry.

Source: user decision during the Q06 discussion.

### [RESOLVED] Q07: API-Product Web-Client Profile

The harness's API-product client-parity profile was generalized from
GWEN's web-UX architecture. It is not a universal API boundary rule.

Decision:

- Remove web-client/API parity from reusable harness material.
- Do not migrate it into Ponytail as either a general or opt-in skill.
- Keep it in GWEN's project-local customizations.

Source: user decision in the Q07 discussion.

### [RESOLVED] Q08: Published Clients And Language Bindings

The harness names SDKs in scope, monetary propagation, compatibility,
and acceptance examples. Projects may have no SDKs or may use other
independently released client forms.

Decision:

- Generalize the rule beyond SDKs and language bindings.
- When a host declares generated or maintained artifacts that mirror a
  contract, update and validate every affected artifact with the
  contract change.
- Do not assume an artifact kind or implementation language.

Source: user decision in the Q08 discussion.

### [RESOLVED] Q09: Always-On Core And Ponytail Modes

Ponytail defaults to an active `full` mode and permits `off`. Harness
defaults are intended to remain active independently of an optimization
persona.

Decision:

- All rules except aggressive code compaction are always active.
- Aggressive code compaction is enabled by default.
- Turning off aggressive compaction does not disable another rule.
- Retain Ponytail's existing `lite`, `full`, and `ultra` levels to
  control compaction intensity.

Source: user decision during the Q09 discussion.

### [RESOLVED] Q10: Project Instructions And Portable Rules

Ponytail uses root `AGENTS.md` as both repository-local instructions and
a portable fallback artifact. The harness treats project-local
instructions as configuration rather than reusable policy.

Decision:

- Maintain one repository-neutral policy source for portable rules.
- Generate host adapters and runtime instruction payloads from it.
- Keep specialized skills as separately triggered modules.
- Use project `AGENTS.md` files only for local configuration and skill
  bindings.
- Use Ponytail's root `AGENTS.md` to configure the Ponytail repository,
  not as a portable rule artifact.

Source: user approval in the Q10 discussion.

### [RESOLVED] Q11: Product And Marketing Skills

`ponytail-gain` exposes benchmark marketing as an agent skill, while
`ponytail-help` describes product commands. These are not coding
workflows.

Decision:

- Remove `ponytail-gain` entirely as a skill and command.
- Keep benchmark claims and evidence in documentation and benchmark
  artifacts.
- Retain `ponytail-help` as an explicit command, not as a skill.

Source: user decision in the Q11 discussion.

### [RESOLVED] Q12: Examples And Platform-Native Guidance

Ponytail examples demonstrate code reduction but some intentionally omit
error handling, cleanup, compatibility, or complete validation.

Decision:

- Delete the `examples/` directory.
- Delete its dedicated benchmark-output generator.
- Remove inbound README links to the deleted directory.
- Retain benchmark inputs, correctness checks, results, and reproduction
  tooling under `benchmarks/`.

Source: explicit user direction in the Q12 discussion.

### [RESOLVED] Q13: Skill Registry And Generated Surfaces

The harness has an enabled/disabled registry. Ponytail discovers
directories and hardcodes some host-specific skill metadata and command
lists.

Decision:

- Maintain one declarative registry for skills and commands.
- Record activation status and host exposure in that registry.
- Generate host manifests and adapters from the registry.
- Do not infer activation from directory presence.

Source: user approval in the Q13 discussion.

### [RESOLVED] Q14: Project-Local Skill Activation

The harness installer can add project-local skill directories.
Ponytail's plugin distribution exposes repository-bundled skills across
many hosts.

Decision:

- Store project-local skills under `.agents/skills/` in their owning
  repository.
- Put project-wide skills in the management repository and
  component-specific skills in the owning component repository.
- Declare every project-local skill root and binding explicitly.
- Register or link project-local skills through the selected host
  adapter without copying them into Ponytail.
- Do not discover project-local skill roots implicitly.

Source: user approval in the Q14 discussion.

### [RESOLVED] Q15: Source-History Import

The standalone harness will remain available during transition, but its
reusable content and authorship must enter Ponytail with clear
provenance.

Decision:

- Do not merge the repositories at the Git-history level.
- Apply changes directly to Ponytail.
- Commit each individually meaningful change-set separately.
- Preserve source provenance and authorship in affected files and
  commit messages.

Source: user decision in the Q15 discussion.

### [RESOLVED] Q16: Publication Identity

The current package and manifests use Dietrich Gebert's npm scope,
repository URLs, authorship metadata, and marketplace coordinates.

Decision:

- Publish from `github.com/alexbaretta/ponytail`.
- Use the npm package name `@alexbaretta/ponytail`.
- Identify Alex Baretta as fork publisher and maintainer.
- Retain Dietrich Gebert as Ponytail's original author.
- Update manifests, marketplace ownership, generated metadata sources,
  and current installation documentation to use the fork's coordinates.

Source: explicit user direction in the Q16 discussion.

### [RESOLVED] Q17: Validation And Benchmark Separation

Ponytail's ordinary root test suite includes benchmark correctness
checks with external Python dependencies. Harness validation is
dependency-light.

Decision:

- Separate all benchmark features from the core Ponytail distribution.
- Keep benchmark code, dependencies, commands, tests, claims, and
  publication concerns in an optional isolated subsystem.
- Do not execute benchmark code or require benchmark dependencies during
  core setup, development, testing, packaging, or publication.
- Permit core documentation to link to benchmark material without making
  benchmark results part of ordinary correctness or acceptance.

Source: explicit user direction in the Q17 discussion.

### [RESOLVED] Q18: Gemini CLI Support

Decision:

- Remove the Gemini CLI extension adapter.
- Rename the shared Claude Code and Codex lifecycle definition to
  `hooks/hooks.json`.
- Let Codex discover that conventional path automatically.
- Point Claude Code's manifest at the same file.
- Record the removed support and restoration conditions in
  `tech_debt.md`.

Source: explicit user direction after Q17 was raised.
