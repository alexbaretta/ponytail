## Feature F01: Build-Impact Contract

### [DONE] Tasklet S01-F01-T01: Define Project Configuration Schema

Define the approved project-local configuration file with:

- an ordered collection of bundled or custom impact adapters;
- one or more uniquely owned build targets per adapter;
- one `tsconfig` and build command per TypeScript target;
- optional additional inputs consumed by each target; and
- one executable and argument vector per custom adapter.

Reject aliases, unknown fields, duplicate target names or ownership,
ambiguous relative paths, and adapters without owned targets.

Validation: focused schema fixtures cover the smallest valid TypeScript
configuration, multiple TypeScript targets, mixed TypeScript and custom
adapters, multiple custom adapters, and invalid duplicate ownership.

### [DONE] Tasklet S01-F01-T02: Define Query Protocol

Define a versioned JSON request containing the project root and intended
changed paths. Define a versioned response containing:

- affected target names;
- their configured build commands;
- concise changed-file reasons; and
- per-adapter indeterminate results when impact cannot be determined.

Keep complete compiler input lists out of the response.

Validation: exact request and response fixtures cover affected, unaffected,
partially affected, and indeterminate mixed-adapter results, including paths
with spaces and deleted paths.

## Feature F02: TypeScript Adapter

### [DONE] Tasklet S01-F02-T01: Resolve Project TypeScript

Resolve the TypeScript compiler from the governed project so the query uses
the same compiler version as the build. Do not download or bundle a compiler
and do not fall back to a global `tsc`.

Validation: focused tests prove project-local resolution and explicit failure
when TypeScript is unavailable.

### [DONE] Tasklet S01-F02-T02: Query Compiler Inputs

Run the resolved compiler with the configured `tsconfig`,
`--listFilesOnly`, and noninteractive output. Normalize repository-owned
paths, retain target ownership internally, and discard dependency paths
outside the project unless they are configured project inputs.

Validation: a minimal TypeScript monorepo fixture proves direct imports,
project references, independent targets, and no emitted build output.

### [DONE] Tasklet S01-F02-T03: Match Intended Paths

Compare normalized intended paths with compiler inputs and configured
additional inputs. Treat each target's effective `tsconfig` chain as an
invalidating input. Return only affected targets, commands, and concise
reasons.

Validation: focused tests prove source changes require the owning build while
unowned documentation, project records, tests, and runtime-only environment
files do not.

## Feature F03: Custom Adapter And CLI

### [DONE] Tasklet S01-F03-T01: Invoke Custom Query Commands

Invoke every configured custom adapter without shell interpolation. Send the
canonical request on standard input and validate each response against the
canonical response schema and its declared target ownership.

Validation: focused tests cover multiple commands, success, malformed output,
undeclared or duplicate targets, nonzero exit, and paths containing spaces
without executing a shell.

### [DONE] Tasklet S01-F03-T02: Compose Adapter Results

Run every configured bundled and custom adapter against the same intended
paths. Merge uniquely owned affected targets. Preserve successful results when
another adapter fails, but report the failed adapter's targets as
indeterminate and never reduce a partial result to "no build required."

Validation: composition tests cover TypeScript plus C++, multiple custom
adapters, disjoint affected targets, duplicate ownership, and one failed
adapter alongside one successful adapter.

### [DONE] Tasklet S01-F03-T03: Add Build-Impact CLI

Add the skill-owned CLI entry point that reads the approved configuration,
accepts intended paths safely, dispatches to every configured adapter, and
emits only the merged canonical response.

Validation: CLI tests cover affected, unaffected, and indeterminate exits and
machine-readable output.

### [DONE] Tasklet S01-F03-T04: Package The Tool

Register the new reusable skill for supported hosts, include its CLI and
schema resources in distributions, and regenerate host adapters through
canonical generators.

Validation: registry, OpenClaw resource, distribution, manifest, and installer

## Feature F04: Policy And Workflow

### [DONE] Tasklet S01-F04-T01: Update Portable Policy

Add the canonical condition-and-action rule:

- when the query reports affected targets, build them once after their final
  input edits;
- when it reports no affected targets, skip the build; and
- when it reports an indeterminate result, resolve the configuration or tool
  failure rather than claiming that no build is required.

Validation: policy conformance tests require the canonical wording at every
compaction level.

### [DONE] Tasklet S01-F04-T02: Update Project Configuration Guidance

Replace the bare full-build-command requirement with the build-impact
configuration owner, query command, target build commands, and non-build
validation commands.

Validation: project-configuration tests require the new keys and reject the
old unconditional build assumption.

### [DONE] Tasklet S01-F04-T03: Update Plan Validation Cadence

Require the build-impact query at tasklet, story, sprint, and plan gates.
Reuse successful build evidence while inputs remain unchanged. Do not run a
build merely because work advances to a higher management level.

Validation: cadence tests cover affected, unaffected, post-build input change,
and unchanged higher-level completion cases.

### [DONE] Tasklet S01-F04-T04: Reconcile Specialized Skills

Make every reusable skill that mentions builds or broader gates reference the
canonical build-impact rule. Preserve stronger packaging, generation, and
release proof only when those artifacts are the requested deliverable.

Validation: a source audit finds no reusable instruction that unconditionally
requires a project build for an unrelated change.
