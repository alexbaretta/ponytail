## Objective

Adopt the graph and tag workflow in Ponytail, preserve historical meaning and
unfinished work, and prove the installed end-to-end experience. Apply Q6's exact
transition rather than assume every active campaign or client can be migrated.

## Draft work packages

1. Reconcile Ponytail's authorized active requirement/obligation/acceptance/test
   and code annotations, configuration and generated reverse views. Do not map
   old inventory/gate obligations to atomic requirements by ID rename. Inventory
   semantic gaps and resolve the plan-owned ones; never infer passing proof.
2. Implement/prove the approved bounded migration/adoption operation if needed.
   Preserve source/branches/tags, active assignments, external pending operations
   and original historical bytes. Preview and retry safely within this project;
   migrate no unrelated live rows and erase no ledger/history automatically.
3. Exercise graph ingestion → completeness → focused tagged worker candidate →
   independent review → serialized fast-forward → final QA/tag in disposable
   fixtures, including rejection and recovery paths from preceding sprints.
4. Verify native host capabilities separately in an explicitly authorized pilot:
   session activity observation, goal continuation/blockers, messaging, local
   review, replacement/resumption and timer recovery. No workers or outside-path
   checkouts are created without applicable authority. Report host limits and
   failed/unavailable gates; fixture success is not live continuity proof.
5. Test isolated installation/upgrade/uninstall and every enabled host's generated
   exports; remove retired owned assets without removing user-owned files.
   Complete project instructions, documentation and final source/consumer audit.
6. Run final configured acceptance after final relevant inputs, record the exact
   candidate's results through the new tag mechanism, and close lifecycle records
   only when all outcomes and final gates are established.

## Acceptance and validation

Run configured build-impact selections and required affected integration Arcs.
Final core acceptance is `npm test`, rule-copy and version checks, with registry,
manifests/adapters, generated runtime, structural/indexed traceability, TSTS,
installers, MCP and bundled-subproject checks accounted for once. Fix any required
focused-selection configuration gap instead of substituting a broader command.

Required evidence: graph coverage cannot mask missing acceptances; no fake T/I
decrease; exact review/tag/candidate identity; honest disturbances/monitoring;
blocked worker retention/replacement; no stale or duplicate integration; read-only
historical compatibility; and no tracked validation output or evidence-only
commits produced by the adopted workflow. Do not publish a release or tags to a
remote, rewrite history, or install globally as an implicit acceptance step.

Final acceptance remains pending if actual host continuity cannot be demonstrated
under the approved pilot. The coordinator remains responsive while delegated QA
runs only if that delegation was selected and proven, retaining final acceptance
responsibility. All sprint outcomes are currently planned, not implemented.
